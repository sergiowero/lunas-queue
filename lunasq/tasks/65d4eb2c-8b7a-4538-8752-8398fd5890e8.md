Removing a canceled task's worktree is already built. On cancel, the reconciler calls `worktree remove`, but it never forces it. If the worktree has uncommitted changes, herdr refuses, the error is logged once, and the worktree stays open for good. That's probably what you saw.

The question is what should happen to a canceled task's uncommitted changes:
- **Force always:** remove the worktree anyway and discard the uncommitted changes. The branch is kept.
- **Commit WIP then remove:** commit the changes to the task branch as a work-in-progress commit (not pushed), then remove the worktree.
- **Keep current, notify:** don't force; tell you when a worktree is blocked and give you a way to force it from the UI or CLI.
- **Other bug:** the worktree was clean and still wasn't removed, and you describe what happened.

I also noted a smaller gap in the question. A task whose bootstrap failed, like this one's first attempt, has no saved worktree path. If it's canceled, its worktree is only picked up by the periodic orphan sweep, about every 10 minutes, rather than right away.
