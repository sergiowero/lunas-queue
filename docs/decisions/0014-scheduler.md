# 0014 — Scheduler: ready set, score and limits

- Status: accepted
- Date: 2026-10-29
- Unit: UW-13 · Code: `packages/schemas/src/scheduler.ts`, `packages/domain/src/scheduler.ts`, `packages/db/src/scheduler-state.ts`, `packages/server/src/scheduler/`

## Context

`docs/design.md` (§Scheduler) defines the ready set, the score (base priority + aging + boost), priority inheritance and four levels of limits (global with a default of 5, project, agent type and phase), without preemption. It did not say what counts as an occupied slot, what the per‑project limit measures, since when aging runs or where the global limits live. ADR 0010 left it to UW-13 to decide what to do with the dependents of a canceled task.

## Decision

- **Rules in the domain.** `schedule(snapshot, projects, config, now)` is pure and returns `{ dispatch, escalate }`. `rankReady` computes the ordered ready set and `pendingPhase` maps state to phase: draft → refine, in\_progress → implement, verification → verify. Delivery runs inside the verifier's Run (ADR 0007), so it is not scheduled separately.
- **Ready set.** Tasks with sub‑state `queued` in a state with an agent whose dependencies all have `prState = merged` enter. A dependency absent from the snapshot does not satisfy.
- **Score.** `effective priority + agingPointsPerHour × hours in ready + boostPerDescendant × live descendants`. The effective priority is the maximum between the base priority and that of the live descendants (transitive inheritance); it stops inheriting when the blocked one reaches a terminal state. Tie‑break: age (`createdAt`) and then id. Defaults: 10 points per hour and 25 per descendant, in the units of the priority.
- **readySince.** Computed by the database: the most recent of the task's creation, its last `task.transitioned` and the `updatedAt` of its already merged dependencies. This way aging survives a restart. A retry (`run_failed` back to queued) restarts it on purpose: the task waits again from there. Editing the priority (`task.updated`) does not restart it. Until UW-14 records the merge time, the merged dependency's `updatedAt` approximates it.
- **Slots.** Every task in a state with an agent with sub‑state `running` or `waiting_human` occupies a slot: with an open question the agent may still be alive (`answer` goes back to running). The human gates (refined) and needs\_human do not occupy.
- **Limits.** Global (`globalConcurrency`, default 5), per phase (`phaseConcurrency`, only refine, implement and verify: `SchedulablePhase`) and per agent type (`agentKindConcurrency`) live in `SchedulerConfig` (`@lunasq/schemas`), which the process receives on startup. The per‑project limit is `ProjectLimits.concurrency` (ADR 0008) and counts the **project's live agents in all phases**, not only those in in\_progress: it is what bounds load and conflicts, and guarantees the cap under any mix of phases. The agent type comes from the project's `phaseProfile`, also for live agents (it is not read from the Run); a live agent of a project without configuration counts in the global, project and phase limits, but not in the type one. A task whose project has no configuration is not dispatched. `Occupancy` counts the slots and decides whether one more fits; `schedule` uses it to plan and UW-16's claim uses it to revalidate with a fresh snapshot, with the same rules.
- **No preemption.** The plan walks the ready set by score and takes each task that fits in the four levels; one that does not fit is skipped and the next follows. Live agents are never interrupted.
- **Dependencies that will not be delivered.** If a dependency has its PR closed without merge or is canceled without a merged PR, the scheduler escalates the direct dependents that are not terminal, are not in needs\_human and do not have a live agent (escalating one with an agent would release its slot with the agent running; it is escalated when its Run ends), with `escalate` and `reason: dependency_pr_closed` (the reason is reused for cancellation), with `expected` so as not to overwrite a concurrent change. It leaves needs\_human when the human removes the edge and resumes; if they resume it without removing it, it is escalated again.
- **Snapshot.** `SchedulerStateReader.snapshot()` (port in the domain, `SchedulerStateRepository` in db, `InMemorySchedulerStateReader` in tests, shared contract) returns the live tasks, the terminal ones that some live one depends on and the edges of the live ones, read in a transaction.
- **Process.** `Scheduler` (server) runs a pass with `run()`. Passes do not overlap: a request during a pass is grouped into one more pass, and one that arrives when the pass is already exiting relaunches it at the end, as in the outbox publisher. A failure when escalating is reported with its task and does not skip the pass's dispatches. It subscribes to `*` in the `OutboxPublisher` (the handler only requests the pass, it does not wait for it) and has a tick (`tickIntervalMs`, default 30 s, minimum 1 s) that picks up aging and the changes that do not go through the outbox. After escalating it wakes the publisher. `stop()` cuts the tick and the subscription and waits for the pass in progress, which dispatches no more decisions.
- **`Dispatcher` port.** `dispatch(decision)` resolves when the claim was confirmed (the task is in running) or rejects. The scheduler waits for each dispatch before the next, so the next pass sees the slots occupied. A rejection is reported with `onError` and does not stop the pass.

## Consequences

- **UW-16** implements `Dispatcher`. Inside the claim it must revalidate `expected` (with `transitionTask` and `dispatch`) and the limits with `Occupancy` over a snapshot read in the same transaction: the plan was computed earlier and another process (the CLI) could have dispatched in between. It also composes the process: creates the `Scheduler` with the publisher and calls `start()` and `stop()`.
- **UW-14** records the merge in the task (`prState`, and with it its `updatedAt`); if it adds an event with the merge time, `readySince` can use it instead of `updatedAt`.
- **UW-17** must not treat a task in `waiting_human` as fallen: it occupies a slot on purpose.
- **Global limits.** They are configured when the process starts; there is no API or table to change them live in v1.
- **Cost per pass.** Each pass reads all live tasks and their edges, and the ranking walks each candidate's descendants. With v1's volume it is enough; if it grows, the graph is cached per pass or the descendant count is computed only once.
