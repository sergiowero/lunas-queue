# 0012 — Worktree lifecycle: deterministic branch, bootstrap before persisting and orphans

- Status: accepted
- Date: 2026-10-29
- Unit: UW-09 · Code: `packages/domain/src/worktrees.ts`, `packages/db/src/task-worktrees.ts`, `packages/adapters/src/process/`, `listWorktrees` in `packages/adapters/src/herdr/`, `packages/server/src/worktrees/`

## Context

`docs/design.md` (§Worktree lifecycle) fixes one task = one worktree = one branch from the first dispatch until the merge: create from the base branch, run the bootstrap, reopen in later phases, remove after the merge or the cancellation and detect orphans. ADR 0004 made clear that `worktree create` is not idempotent. UW-09's criterion: two tasks of the same repo work in parallel and repeating the operation duplicates nothing.

## Decision

- **Branch.** `lunasq/<taskId>` (`taskBranch` in domain). The id must be a single git‑safe segment (UUIDs are); `taskIdFromBranch` inverts it. Only branches with that prefix are considered LunasQ's. The checkout path is chosen by herdr (`~/.herdr/worktrees/<repo>/<slug>`) and the one it returns is stored.
- **Remote base branch on creation.** Before `worktree create`, `git fetch --quiet origin <baseBranch>` runs in the project's checkout and the worktree is created from `origin/<baseBranch>`. This way a dependent task starts from a base that already includes the merge of its dependencies even if the local `main` is behind (checked with herdr 0.9.5). If the fetch fails, `base_fetch_failed` and nothing is created. On reopening no fetch is done.
- **The DB says whether the worktree is ready.** `ensure` ensures the project's workspace, does `ensureWorktree` and runs the bootstrap if the checkout was just created or if `worktree_path` in the DB does not match the path. Only afterwards it stores `branch` and `worktree_path`. If the stored path does not match, it is cleared before running the bootstrap. A bootstrap that fails (exit ≠ 0 or timeout, 30 min by default) gives `bootstrap_failed` and leaves the path null, so the next `ensure` retries it: **the project's bootstrap must be idempotent**. It runs with `sh -c` in the worktree and receives `LUNASQ_PROJECT_ID`, `LUNASQ_TASK_ID`, `LUNASQ_BRANCH`, `LUNASQ_BASE_BRANCH` and `LUNASQ_WORKTREE`.
- **Bootstrap as a child process, not in a pane.** It runs with the new `ProcessRunner` from `adapters` (`ShellProcessRunner`, with its fake): it has to finish before persisting and before the agent starts, and its result decides the `ensure`. herdr's `worktree.created` event is not used. The runner runs in its own process group (the timeout also kills the children), does not throw on exit code and keeps the last 256 KiB of each stream. It finishes when the shell exits: children that keep the pipes open (a daemon, a `… &`) get 200 ms and then the group is killed, so a background process does not hang the bootstrap. With `detached` the children survive a server crash. UW-10 and UW-11 can reuse it or continue with the herdr pane from `docs/tech-stack.md`.
- **Serialization per task and per project.** `ensure`, `remove` and the orphan cleanup take an in‑process lock per task id (`KeyedLock`): two concurrent `ensure` of the same task do not do two `create`. Inside, what touches the repo and herdr (ensuring the workspace, `worktree list`, `git fetch`, `create`, `remove`) goes under a lock per project, because `ensureWorkspace` is not atomic in herdr (snapshot and then create) and git locks refs and `.git/config` on concurrent fetch and create. The bootstrap runs outside the project lock, so a project's tasks are prepared in parallel. The order is always task → project. A single dispatcher is enough in v1 (`docs/tech-stack.md`). The herdr fake yields the turn between looking up and creating, like the real one, so the tests see these races.
- **Tasks that already released their worktree.** `worktreeReleased`: `cancelled`, or `completed` with `prState = merged`. `completed` arrives when the PR opens and the task can go back to in progress, so with the PR open, closed without merge or without a PR the worktree is kept. `ensure` rejects a released task with `task_released`.
- **Removing.** `remove` looks up the branch in `worktree list`; if the worktree is closed it reopens it (herdr needs its workspace) and does `worktree remove`, which keeps the branch. Then it sets `worktree_path` to null. Without a worktree it is a no‑op (`removed: false`). With uncommitted changes herdr answers `dirty_worktree_requires_force` and the service translates it to `dirty_worktree`. It is only deleted with `force`.
- **Orphans.** `findOrphans` crosses `worktree list` with the tasks of all projects (two projects can share a repo): an orphan is a `lunasq/*` worktree whose task does not exist (`task_not_found`) or that has already released its worktree (`task_released`). Foreign branches and detached‑HEAD checkouts are never touched. `cleanupOrphans` removes them without forcing, revalidates each task and lists again under the locks, and reports failures (e.g. `dirty_worktree`) without stopping. If it had to reopen a worktree to remove it and the remove fails, it closes it again. Triggering removal after the merge or the cancellation, and the periodic cleanup, are left to whoever consumes the service (UW-17, UW-26).
- **herdr adapter.** `listWorktrees(workspaceId)` returns the repo's linked worktrees (`worktree list` without the main checkout), open or not; a removed one no longer appears even if its branch remains. The contract suite covers it against the fake and against real herdr. The fake models `dirty_worktree_requires_force` with `setWorktreeDirty(path)`.

## Consequences

- The project's workspace is looked up by label (`ensureWorkspace` with the project name), because Project does not yet store its herdr id (ADR 0008, left for UW-16).
- A worktree created from `origin/<base>` ends up with upstream `origin/<base>`: delivery (UW-26) must push with an explicit refspec (`git push -u origin lunasq/<id>`).
- `findOrphans` and `cleanupOrphans` create the project's workspace in herdr if it does not exist, like the rest of the operations.
- Looking up the workspace by label can adopt one that the user created with the project's name, or duplicate it if the project is renamed. It is resolved when UW-16 stores the id in Project.
- Recreating an active task's worktree after a `remove` reuses its branch: herdr 0.9.5 accepts it (a contract suite case).
- The branch of a removed task stays in the local repo; deleting it is not part of v1.
