# UW-10 — Per-phase hooks: reading from the base branch, execution in a pane and commit with trailers

- Status: accepted
- Date: 2026-10-29
- Unit: UW-10 · Code: `packages/schemas/src/hooks.ts`, `packages/domain/src/hooks.ts`, `packages/adapters/src/git/`, `packages/adapters/src/process/pane.ts`, `runInPane` in `packages/adapters/src/herdr/`, `packages/server/src/hooks/`

## Context

`docs/design.md` (§Per-phase hooks) fixes the hook points, that the scripts live in the repo's `lunasq/hooks/<point>/`, that they run in alphabetical order in a herdr pane with a `block` or `warn` policy and a timeout per script, and that LunasQ reads them from the base branch, never from the task's branch. It did not fix the format of `lunasq/hooks/config`, how to know the exit code of something that runs in a pane, or what to do with changes that were already in the worktree. UW-10's criterion: the hooks run in order and a hook modified in the task's branch is never executed.

## Decision

- **Points.** `HookPoint` (schemas) with the 10 points: `before_*`/`after_*` of refinement, implementation, verification and delivery, `after_merge` and `on_failure`. `hookPointPhase` gives each one's phase (`LUNASQ_PHASE`); `after_merge` and `on_failure` have none.
- **`lunasq/hooks/config` is JSON**, validated with Zod (`HooksConfig`), with no new dependencies. Grouped by point and script name:
  ```json
  { "before_delivery": { "10-bump-version": { "timeoutSeconds": 300, "policy": "warn" } } }
  ```
  A script without an entry uses the defaults: policy `block` and 10 minutes. Entries for scripts that do not exist are ignored. A config that is not JSON or does not satisfy the schema blocks the point (if it has scripts) without running anything: the intent is not guessed.
- **What a hook is.** A regular file with mode `100755` in the commit, directly inside `lunasq/hooks/<point>/`. Non‑executable ones (helpers such as `lib.sh`) are copied next to the scripts but do not run; symlinks, submodules and subdirectories do not count (a symlink could point into the worktree). Order: by code units of the name, no locale.
- **Always from `origin/<base>`.** Before each point, `fetch` in the project's checkout: the sha comes from `git ls-remote` (`origin/<base>` is not reread, since it lives in the common gitdir and a worktree could move it between the fetch and the read), and scripts and config are read from that commit with `ls-tree`/`cat-file`. The point's files are copied to a private directory per execution (`mkdtemp`, 0700, in the tmpdir by default), that copy is executed and the directory is deleted at the end. Nothing is read from the worktree or the task's branch, committed or not. A change to a hook takes effect when its PR reaches the base branch. If the fetch or the read fails, the point blocks (`baseRef: null`): without the base it is not known what to run.
- **Git adapter** (`@lunasq/adapters`, `RealGit` + `FakeGit` + a contract suite that runs in `pnpm test` against temporary repos): `fetch`, `resolveCommit`, `listFiles`, `readFile`, `isDirty` and `commitAll`. `execFile` without a shell, `GIT_TERMINAL_PROMPT=0`, a 60 s timeout (5 min for the fetch) and `--end-of-options`. Every command runs with `GIT_NO_REPLACE_OBJECTS=1` (a `git replace` from a worktree, which shares `refs/replace`, would change the base's content for all checkouts), `core.hooksPath=/dev/null` (no git hook of the repo runs in LunasQ commands, not even a pre-commit defined by the task's branch) and `core.fsmonitor=false`. If a commit fails, the `add` is undone (`reset`) so as not to leave the index staged. `addDetachedWorktree` and `removeWorktree` open and delete temporary checkouts. The trailers go as their own paragraph of the message: with `git commit --trailer`, a one‑line subject with `: ` (`chore(lunasq): …`) is taken as a trailer block and they end up stuck together with no blank line (checked with real git).
- **Execution in a pane.** `herdr pane run <pane> <command>` writes the line into the pane's shell and returns immediately, without an exit code (herdr 0.9.5). `runInPane` is added to the herdr adapter (real, a fake that actually runs the command, and a contract, also against real herdr). `HerdrPaneRunner` implements the `ProcessRunner` interface: it opens a pane with `pane split --cwd --env` from the worktree's root pane, runs a wrapper that sets cwd and env again (the pane shell's rc files may change them), gives `/dev/null` as stdin, pipes the output through `tee` to a log and writes the exit code with an atomic rename, waits for that file, returns the last 256 KiB of the log as `stdout` and closes the pane. If the timeout expires it closes the pane, which kills the command (`exitCode` 137, `timedOut`). If the pane disappears earlier (confirmed every 2 s with `snapshot`), it is a failure with `exitCode` 129. UW-11 can reuse this runner for the test gate.
- **Hook context.** `LUNASQ_PROJECT_ID`, `LUNASQ_TASK_ID`, `LUNASQ_HOOK_POINT`, `LUNASQ_WORKTREE` (the hook's cwd), `LUNASQ_BRANCH`, `LUNASQ_BASE_BRANCH` and, when they exist, `LUNASQ_RUN_ID`, `LUNASQ_PHASE`, `LUNASQ_PR_URL` and `LUNASQ_PHASE_RESULT`. The env is set in the pane, which inherits herdr server's, not LunasQ's.
- **Result.** A hook passes with exit 0 and no timeout. A failure reading the base or preparing the execution (directory, worktree, temporary checkout) blocks the point and is recorded as `error` in `hook.point_completed`. A failing `block` stops the point's following ones; a `warn` is recorded and the point continues. The point ends `passed`, `warned` or `blocked`. A runner that throws (herdr down) counts as a hook failure.
- **Recording.** Each script leaves `hook.executed` (point, script, base sha, Run, policy, timeout, exit code, timedOut, duration and the last 16 KiB of stdout+stderr) and each point with scripts, `hook.point_completed` (result, script that blocked, earlier error, commit). Both with actor `system` and published in the outbox. A point without scripts records nothing and does not ensure the worktree. The evidence file `lunasq/tasks/{id}.md` belongs to UW-24, which reads these events.
- **Escalation.** A `blocked` point sends the task to `needs_human` with `escalate` and `reason: hook_failed`, except in `after_merge` (the task has already finished) and `on_failure` (the Run has already failed): there it is only recorded. If the task can no longer escalate (e.g. it is already in needs_human), the failure stays in the Event log and `escalated: false`.
- **Committing the changes.** At the points that run in the worktree, if the point did not block and the hooks left changes, `commitAll` with message `chore(lunasq): hooks <point>` and trailers `LunasQ-Task` and `LunasQ-Run` (if there is a Run). If the worktree already had uncommitted changes before the hooks, nothing is committed (`commitSkipped`, and the point ends `warned`): it would mix in the agent's changes. A commit that fails (e.g. a pre-commit of the repo) blocks the point. Repeating without changes creates no commits. `after_merge` never commits.
- **Concurrency.** The points of the same task are serialized (`KeyedLock` per task); the fetches, per project checkout.
- **`after_merge` runs in a temporary checkout** in detached HEAD at the base commit just read (`git worktree add --detach`), with a pane opened from the project's workspace, and is deleted at the end. The user's checkout may be on another branch or behind: a deploy from there would deploy other code.
- **`after_merge`** is triggered with `subscribeAfterMergeHooks`: an outbox subscriber to `task.pr_state_changed` with `to: merged` that calls `run` without awaiting it, so a long deploy does not hold back the rest of the subscribers.
- **`on_failure`** is triggered by the `run.failed` event (`RUN_FAILED`, payload `runId`, `phase`, `reason`). `closeRun` appends and publishes it in the same transaction that closes a Run with result `failure`, so it covers `report_failure`, `PhaseDispatcher.failRun` (launch error, watcher, reconciler) and `providers_unavailable`, and exactly once per Run: a repeated close finds the Run closed and appends nothing. Runs closed as `success` or `cancelled` (including a paused dispatch or a blocked `before_*` point) emit nothing. `subscribeOnFailureHooks` calls `run` with `point: on_failure`, the Run id and the reason as `LUNASQ_PHASE_RESULT`, without awaiting it, like `after_merge`; a failure of the hook is only recorded and never escalates. Delivery is at least once, so `on_failure` hooks must be idempotent.
- **`before_refinement` and `before_implementation`** run in the dispatcher before the agent is started (ADR uw-16-dispatcher); a blocked point cancels the Run instead of failing it. **`after_refinement`** runs in `submit_spec` after the handoff validates and before the spec is recorded; if it blocks, the call answers `hook_blocked`, no version is created and the task is in `needs_human`, so a retry does not run the hooks again.
- **View.** `HookService.listHooks(projectId)` returns, per point, the base branch's scripts with their content, policy and timeout, and the config's error if any. The routes and the view belong to UW-25; the latest executions come from the events.

## Consequences

- **Each phase calls `HookService.run`** at its point: UW-16 (`before_refinement` and `before_implementation` on dispatch; `on_failure` through `run.failed`), UW-23 (`after_implementation` after the test gate, `before/after_verification`), UW-26 (`before_delivery` before the rebase and push, `after_delivery` after creating the PR) and refinement (`after_refinement` after `submit_spec`). The caller decides not to continue if the result is `blocked`.
- **Hooks must be idempotent**: a phase repeats through rework or retries, and `after_merge` can repeat because the outbox delivers at least once. If the process crashes while an `after_merge` runs, it is not retried on its own (the message was already marked); reconciliation (UW-17) can detect it by the missing `hook.point_completed`.
- **Without network there are no hooks**: a failed fetch blocks the point even if the project has no hooks. It is consistent with the worktree (ADR 0012), which is not created without a fetch either.
- **A hook that leaves a background process** with the output open keeps the wrapper's `tee` alive until the timeout. Hooks must redirect the output of what they leave running.
- **Limit of the guarantee.** The agent runs as the same system user and its worktree shares the project's gitdir. What LunasQ closes: hooks and config from the branch or worktree, `refs/replace`, moving `origin/<base>` and the repo's git hooks. What it does not: an agent that rewrites `remote.origin.url` in the shared config or writes into another execution's private directory while it runs. Closing it requires isolating the agent from the common gitdir (sandbox), outside v1.
- The hooks' fetch and `WorktreeService`'s use different locks; if they coincide on the same checkout, git may reject one because of the refs lock and the point blocks. With a single dispatcher in v1 it is rare; if it bothers, the per‑project lock is shared.
