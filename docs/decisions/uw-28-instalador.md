# UW-28 — Instalador: `lunasq install`, `doctor` y `start`

- Estado: aceptada
- Fecha: 2026-10-29
- Unidad: UW-28 · Código: `packages/cli/src/` (`install.ts`, `doctor.ts`, `assets.ts`, `config.ts`, `paths.ts`, `main.ts`, `bin.ts`), `packages/cli/scripts/build.ts`, `packages/server/src/runtime/`

## Contexto

`docs/tech-stack.md` define un binario `lunasq` publicado en npm con tres comandos. `install` verifica herdr, Claude Code y `gh`, instala la integración de herdr para Claude Code, copia skills y subagentes, registra el LunasQ MCP y configura la telemetría. El criterio de UW-28: una máquina limpia queda lista con un solo comando y `lunasq doctor` en verde. Las unidades anteriores dejaron pendientes para esta: la ruta del archivo MCP y la URL del servidor (ADR uw-16-dispatcher), el settings de hooks (ADR uw-19-revisores), el destino de las skills (ADR uw-18-skills-fase) y el aviso de toasts apagados (ADR 0009). `app.ts` tampoco montaba todavía el servidor HTTP.

## Decisión

- **Todo en `~/.lunasq/`.** Ahí van `config.json` (`port`, por defecto 7360, y `telemetry`, por defecto `true`), `lunasq.db`, `mcp.json` (ADR 0002) y `claude-settings.json` (ADR uw-19-revisores). `LUNASQ_HOME` cambia el directorio. Skills y subagentes van a `CLAUDE_CONFIG_DIR` o, si no está definido, a `~/.claude`, la misma variable que respeta Claude Code. Las URLs del MCP y de los hooks salen del puerto con `runtimeUrls`, y `install` y `start` usan la misma función.
- **El MCP no se registra a nivel usuario.** Registrar el MCP es escribir el archivo estable que el dispatcher pasa con `--mcp-config --strict-mcp-config`. Con `--strict-mcp-config`, un registro de usuario (`claude mcp add -s user`) no le llega al agente. Además, cada sesión de Claude Code del usuario intentaría conectarse sin run token y el servidor la rechazaría. `docs/tech-stack.md` decía «Registra el LunasQ MCP a nivel usuario» y se corrige.
- **Requisitos que no se instalan.** Si falta herdr, Claude Code o una sesión de `gh`, `install` se detiene antes de escribir nada y lista lo que falta. Las versiones mínimas son las de los spikes: herdr 0.9.5 (ADR 0004), Claude Code 2.1.312 (ADR 0002, ADR uw-19-revisores) y Node.js 26. Un herdr que no habla protocol 22 genera un aviso y no una falla, porque es más nuevo y no está verificado, no incompatible.
- **Integración de herdr.** El estado sale de la línea `claude:` de `herdr integration status`. `install` corre `herdr integration install claude` solo si ese estado no es `current`. herdr instala en `CLAUDE_CONFIG_DIR` y falla si el directorio no existe, así que `install` lo crea antes.
- **Assets como espejo.** Cada carpeta de skill (`assets/skills/<nombre>/`) y `assets/agents/lunasq/` se copian como espejo exacto: un archivo que ya no está en los assets se borra del destino. `doctor` marca como desactualizado un asset editado a mano, e `install` lo restaura. El override por proyecto (`.claude/skills`, `.claude/agents`) sigue siendo la manera de personalizar.
- **Telemetría.** `startRuntime` pasa en el `paneEnv` del dispatcher las variables OTLP de `docs/tech-stack.md` hacia `http://127.0.0.1:<puerto>`. Los atributos por Run (`OTEL_RESOURCE_ATTRIBUTES`) y los endpoints `/v1/metrics` y `/v1/logs` son de UW-20. Hasta entonces Claude Code recibe 404 y descarta los datos. `telemetry: false` en la configuración la apaga.
- **`doctor`.** Cada check termina en `ok`, `warn` o `fail`, con la acción que lo resuelve. Verde quiere decir sin fallas, y en ese caso sale con 0. Revisa Node.js, que better-sqlite3 cargue y aplique las migraciones en memoria (ADR 0003), herdr y su servidor, la integración, Claude Code, `gh auth status`, cada skill, los revisores, la configuración, que `mcp.json` y el settings correspondan al puerto, y la telemetría. Solo avisa si los toasts de herdr están apagados (`[ui.toast] delivery`, ADR 0009) o si engram no está instalado (dependencia débil). La clave de herdr se lee con un lector TOML mínimo, sin agregar un parser. `--json` imprime los resultados para scripts.
- **`start` lo compone `server`.** La matriz de fronteras deja a `cli` depender solo de `server`, así que `startRuntime` (en `packages/server/src/runtime/`) arma el proceso. Abre la base y aplica las migraciones, escucha en `127.0.0.1` antes de componer (con puerto 0 la URL real va en los archivos de Claude Code) y monta `createApp` con `PaneTestGate`, `HookService` y el SSE de notificaciones en `/api/notifications`. Después arranca `OutboxPublisher`, `Orchestrator`, `PrPoller` y los hooks `after_merge`. `stop()` es idempotente y cierra también las conexiones SSE abiertas. `lunasq start` lee la configuración, imprime la URL y se detiene con SIGINT o SIGTERM. El servidor importa `@hono/node-server`, que ya estaba en el stack. `server` reexporta el `ProcessRunner` de `adapters` para las comprobaciones del CLI.
- **Paquete npm.** Node.js no quita tipos dentro de `node_modules`, así que el paquete no puede publicar los `.ts` del monorepo. `pnpm --filter @lunasq/cli build` arma `packages/cli/dist/` con esbuild (dependencia de desarrollo nueva, ya estaba en el lockfile por drizzle-kit). El resultado tiene un solo bundle ESM en `bin/lunasq.js`, con todo salvo better-sqlite3, que es nativo y trae prebuild. A su lado van `drizzle/` y `assets/`, que el bundle busca en `bin/..`, y un `package.json` `lunasq` con `bin` y better-sqlite3 como única dependencia. En el repo, `pnpm lunasq <comando>` corre `src/bin.ts` directo. El workspace `@lunasq/cli` sigue `private`, y lo que se publica es `dist/` (`npm publish packages/cli/dist`).

## Verificación

- Unitarios con un home temporal y un `FakeProcessRunner` que responde como herdr, Claude Code, `gh` y engram. Cubren: una máquina limpia queda en verde tras `install`, repetirlo no cambia nada, cada requisito ausente detiene la instalación sin escribir, y cada check falla o avisa en su caso.
- `startRuntime` con fakes: sirve la API, escribe los archivos con su URL, monta el SSE, pasa la telemetría, `stop` es idempotente y un puerto ocupado falla.
- El bundle se arma en el test, corre `--version` y `doctor --json`, aplica las migraciones y encuentra los assets.
- A mano, en esta máquina con Node.js 26.13, herdr 0.9.5, Claude Code 2.1.314 y `gh` real, sobre un `LUNASQ_HOME` y un `CLAUDE_CONFIG_DIR` temporales: `lunasq install` salió con 0, un segundo `install` no cambió nada, `doctor` quedó en verde con un solo aviso (toasts apagados) y `start` sirvió `/api/projects` y se detuvo con SIGINT.

## Consecuencias

- **UW-02 (hallazgo):** con `start` contra el herdr real del usuario, `session.snapshot` trae agentes sin `name` (sesiones de Claude Code que el usuario abrió a mano y que la integración detecta), y el esquema del adapter los rechaza. Toda pasada de reconciliación falla con `invalid_type` en `snapshot.agents[i].name`. Queda como tarea aparte para el adapter. El piloto (UW-29) la necesita resuelta.
- **UW-20:** monta `/v1/metrics` y `/v1/logs` en `createApp` y agrega `OTEL_RESOURCE_ATTRIBUTES` por Run en el dispatcher. La telemetría base ya llega a cada pane.
- **UW-21:** sirve los estáticos del front end desde `startRuntime`.
- **UW-29:** el piloto usa `lunasq install` y `lunasq start`. Publicar en npm (`npm publish packages/cli/dist`, con la versión subida en `packages/cli/package.json`) queda como paso manual de quien libere, porque necesita credenciales y es una acción externa.
- `doctor` no repite la prueba real de los revisores con Claude Code (ADR uw-19-revisores), porque gasta tokens. Sigue en `pnpm --filter @lunasq/server test:claude`.
- Tampoco pre‑acepta la confianza de carpeta en `~/.claude.json`: el dispatcher ya resuelve el diálogo (ADR uw-16-dispatcher).
