# UW-16 — Dispatcher: claim atómico, despacho reanudable, confianza de carpeta y cierre de fase

- Estado: aceptada
- Fecha: 2026-10-29
- Unidad: UW-16 · Código: `packages/domain/src/dispatch.ts`, `packages/db/src/runs.ts`, `packages/db/src/project-workspaces.ts`, `packages/db/drizzle/0004_dispatcher.sql`, `packages/schemas/src/run.ts`, `packages/adapters/src/herdr/claude-tui.ts` (`sendKeys`), `packages/server/src/dispatcher/`

## Contexto

`docs/design.md` (§Secuencia de despacho) define siete pasos: claim, workspace, worktree, agente, prompt, observar y cierre. ADR 0014 dejó a UW-16 implementar el puerto `Dispatcher`, con dos condiciones: revalidar `expected` y los límites dentro del claim, y componer el proceso. ADR 0002 fija el run token en el entorno del pane y un archivo MCP estable. ADR 0004 dejó pendiente la confianza de carpeta de Claude Code. ADR 0008 dejó pendiente si el dispatcher inyecta el modo Auto. ADR 0008 y ADR 0012 dejaron pendiente guardar el id del workspace de herdr en Project. El criterio de UW-16: una fase se despacha de punta a punta contra el fake y contra herdr real, y repetir el despacho no duplica agentes.

## Decisión

- **Claim atómico** (`claimRun`, db). Corre en una transacción `IMMEDIATE`. Primero compara `expected` con la tarea: repetir una decisión ya aplicada devuelve `stale_state`. Después revisa que la fase corresponda al estado (`phase_mismatch`) y que no quede otro Run abierto (`run_active`; el índice único ya lo impedía). Por último revalida los límites con `Occupancy` sobre un snapshot leído en la misma conexión (savepoint anidado). Si todo cuadra, aplica `dispatch` y crea el Run con token (256 bits, hex), iteración, modelo del perfil, nombre del agente y session id. Si algo no cuadra, no escribe nada.
- **`dispatch` resuelve al confirmar el claim.** El resto de la secuencia (worktree con su bootstrap, que puede tardar minutos) corre en segundo plano. Así el scheduler no queda bloqueado y la pasada siguiente ya ve el slot ocupado. Los fallos de esa parte van a `onError` con su Run.
- **Despacho reanudable.** Cada paso queda registrado en el Run: `herdr_pane`/`herdr_workspace` al abrir el pane y `launched_at` (columna nueva) al mandar el prompt. `launch(runId)` salta lo que ya está hecho:
  - Si herdr ya tiene un agente con el nombre del Run, lo reutiliza.
  - Si el pane guardado sigue abierto y sin agente, arranca ahí el agente.
  - Solo manda el prompt a un agente `idle`. Uno `working`, `blocked` o `done` ya lo recibió.

  - Un agente recién arrancado que aún carga (herdr devuelve `agent_not_ready` con `working` o `unknown`) se espera hasta `idle` o `blocked` antes de decidir.
  - Un pane guardado solo se reutiliza si sigue en el workspace y el checkout del worktree, porque herdr reutiliza ids tras reiniciar.

  Si el Run se cierra mientras se lanza (una cancelación durante el bootstrap), el lanzamiento se detiene en el siguiente paso y cierra lo que abrió. `recover()` relanza los Runs abiertos sin `launched_at`. `Orchestrator.start()` lo llama al arrancar. Un lock por Run evita que `recover` y `dispatch` lancen el mismo a la vez.
- **Nombre del agente.** `t<12 hex del task id>-<fase>-<n>`, con `n` el ordinal del Run en esa fase. herdr limita los nombres a `^[A-Za-z0-9_-]{1,32}$` y un UUID completo no cabe. 48 bits del id hacen improbable una colisión. Si ocurre, la detecta la metadata: un agente con ese nombre cuyo token `run` es de otro Run (o cuyo pane no es el guardado) no se adopta, y el Run falla con `agent_name_taken`.
- **Entorno y args.** El pane se crea con `pane split --env` y las variables `LUNASQ_RUN_TOKEN`, `LUNASQ_TASK_ID`, `LUNASQ_RUN_ID` y `LUNASQ_PHASE` (constantes en `@lunasq/schemas`), más las extra del proceso (`paneEnv`). Los args de Claude Code se arman así: `--model <modelo del perfil>`, los args del perfil, `--mcp-config <archivo> --strict-mcp-config` y `--session-id <uuid>`. Un perfil que ya trae alguno de esos flags falla con `profile_conflict`.
- **Modo Auto (pendiente de ADR 0008).** El dispatcher no lo inyecta ni lo exige: vive en los args del perfil, como dice `docs/design.md` §Decisiones tomadas. El dispatcher solo fija lo que el contrato con LunasQ necesita: MCP y sesión.
- **Confianza de carpeta (pendiente de ADR 0004).** Si `agent start` deja el agente `blocked`, el dispatcher lee la pantalla (`agent read`). Solo si reconoce el diálogo de confianza (`showsTrustDialog`: «Yes, I trust this folder» junto a «No, exit») manda `down enter` con el nuevo `sendKeys` del adapter y espera `idle`. El cursor arranca en «No, exit», así que un Enter a secas cerraría Claude Code. Cualquier otro `blocked` en un agente recién arrancado no se toca: el Run falla con `agent_blocked`. En un agente reutilizado (caída después del prompt), un `blocked` es un permiso de la fase y se respeta. Se descartó pre‑aceptar la carpeta en `~/.claude.json`, porque ese archivo lo escriben los procesos de Claude que estén corriendo. UW-28 puede sumarlo como optimización.
- **Identidad de sesión.** El dispatcher fija el session id nativo (`--session-id`, fuente `native`) en el claim. Al cerrar, si el Run no tiene id nativo, usa el `agent_session` que reporta herdr (`herdr`) o el nombre del agente (`name`). La columna nueva `runs.agent_session_source` guarda la fuente.
- **Workspace del proyecto.** La columna nueva `projects.herdr_workspace_id` se lee y escribe con `ProjectWorkspaceRepository` (puerto `ProjectWorkspaceStore` en domain). No es configuración: `ProjectRepository` no la expone. `WorktreeService` pasa el id guardado a `ensureWorkspace` solo si sigue siendo un workspace principal con el label del proyecto o con un pane en su checkout: herdr reutiliza ids como `w1` tras reiniciar. Después guarda el que resulte, así un proyecto renombrado no duplica su workspace. Sin el store, sigue buscando por label.
- **Cierre de fase.** `closeRun(runId, {result, handoff?, failureReason?})` guarda resultado, handoff e identidad de sesión y cierra el pane, y con él el agente. Es idempotente: gana el primer cierre. Los cierres de un Run se serializan entre sí, sin esperar al lanzamiento. El pane solo se cierra si sigue siendo del Run: tiene su agente, o está vacío en su workspace y en su worktree. No transiciona la tarea. Sobre un Run ya cerrado solo limpia el pane. `failRun(runId, reason)` cierra el Run como failure y, si la tarea sigue en running en esa fase, aplica `run_failed` con los fallos consecutivos de la fase, contados desde el último Run exitoso o el último `resume`, según ADR 0007. Usa el mismo `consecutiveFailures` que `report_failure` (UW-15) más uno por el Run que falla: así cuenta aunque empiece en el mismo milisegundo que el `resume`. También cierra el pane. Un fallo al lanzar (bootstrap, herdr, perfil) usa `failRun`.
- **Observación.** El puerto `RunObserver` (`watch` al lanzar, `unwatch` al cerrar) es para UW-17. Señales, nudges y timeouts quedan fuera de esta unidad.
- **Archivo MCP.** `ensureMcpConfig(path, url)` escribe el archivo de ADR 0002 solo si falta o cambió, con un rename atómico. `Orchestrator.start()` lo asegura antes de despachar. La ruta y la URL las fija quien arranca el proceso (CLI, UW-28).
- **Composición.** `Orchestrator` arma `WorktreeService` (con el store de workspaces), `PhaseDispatcher` y `Scheduler` con los mismos límites. `start()` asegura el archivo MCP, llama `recover()` y arranca el scheduler. `stop()` detiene el scheduler y espera los lanzamientos en curso. El publicador del outbox lo arranca quien lo crea.
- **Integración con el LunasQ MCP (ADR uw-15-mcp-tools).** Las tools de salida cierran el Run en la misma transacción que la transición. El dispatcher no vuelve a cerrarlo: el `Orchestrator` se suscribe a `task.transitioned` en el outbox. Cuando la tarea sale de `running` y su último Run ya está cerrado, llama `releaseRun`, que detiene el agente y cierra el pane. Un Run abierto (el verificador con pass, ADR 0007) no se toca. `RunRepository`, `closeRun` y `consecutiveFailures` son los de UW-15, extendidos con lo que necesita el dispatcher (`forTask`, `active`, `latestForTask`, `recordPane`, `markLaunched`, `close`, `fail`, la identidad de sesión en `closeRun`).
- **`MCP_TOOL_TIMEOUT`.** `submit_for_verification` corre el gate de tests dentro de la llamada (20 min por defecto). El dispatcher fija `MCP_TOOL_TIMEOUT` en el pane a ese timeout más 5 minutos (`DEFAULT_MCP_TOOL_TIMEOUT_MS`); `paneEnv` puede cambiarlo.
- **Migración 0004 editada a mano.** Va después de `0003_runs_context_read` de UW-15. drizzle-kit recreaba `runs` copiando columnas inexistentes, y el `DROP` habría borrado en cascada los `usage_records`. Se usa `ADD COLUMN` con CHECK, igual que en 0002.

## Consecuencias

- **UW-15**: sin cambios en sus tools. Cierran el Run y el dispatcher limpia el pane al ver la transición por el outbox, así que el `OutboxPublisher` debe estar corriendo junto al `Orchestrator`.
- **UW-10**: los puntos `before_*` al despachar y `on_failure` al fallar un Run todavía no llaman a `HookService.run`. Quedan pendientes en esta unidad o en otra.
- **UW-17**: implementa `RunObserver` (suscripción por pane, timeout de fase) y usa `failRun` ante un crash. La reconciliación puede apoyarse en `RunRepository.active()` y en `launch` para relanzar.
- **UW-28**: elige la ruta del archivo MCP y la URL del servidor y se las pasa al `Orchestrator`. `doctor` puede avisar si el diálogo de confianza cambió de texto, porque entonces el dispatcher fallaría con `agent_blocked`.
- **Ventana conocida:** si el proceso cae entre `promptAgent` y `launched_at` mientras el agente sigue `idle`, `recover` repite el prompt. Con Claude Code el agente pasa a `working` de inmediato, así que la ventana es mínima.
- **Riesgo con `--session-id`:** el id nativo se fija en el claim. Si el proceso cae después de que Claude Code creó la sesión y hay que arrancar un agente nuevo en ese Run, se le pasa el mismo id, y Claude Code podría rechazarlo por estar en uso. No está verificado. Lo cubre el piloto (UW-29); si falla, se genera un id nuevo al arrancar un agente fresco.
- **Sin probar con Claude Code real en esta unidad:** que `--session-id` conviva con `herdr agent start` y que el header `${VAR}` se expanda. La expansión quedó probada en el spike de ADR 0002 con herdr. La suite real de UW-16 (`pnpm --filter @lunasq/server test:herdr`) usa un `claude` stub que reproduce el diálogo de confianza y registra args y token. El piloto (UW-29) lo cubre con Claude Code real.
