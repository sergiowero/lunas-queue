# UW-16 — Dispatcher: atomic claim, resumable dispatch, folder trust and phase closing

- Status: accepted
- Date: 2026-10-29
- Unit: UW-16 · Code: `packages/domain/src/dispatch.ts`, `packages/db/src/runs.ts`, `packages/db/src/project-workspaces.ts`, `packages/db/drizzle/0004_dispatcher.sql`, `packages/schemas/src/run.ts`, `packages/adapters/src/herdr/claude-tui.ts` (`sendKeys`), `packages/server/src/dispatcher/`

## Context

`docs/design.md` (§Dispatch sequence) defines seven steps: claim, workspace, worktree, agent, prompt, observe and close. ADR 0014 left UW-16 to implement the `Dispatcher` port, with two conditions: revalidate `expected` and the limits inside the claim, and compose the process. ADR 0002 fixes the run token in the pane's environment and a stable MCP file. ADR 0004 left Claude Code's folder trust pending. ADR 0008 left pending whether the dispatcher injects Auto mode. ADR 0008 and ADR 0012 left pending storing the herdr workspace id in Project. UW-16's criterion: a phase is dispatched end to end against the fake and against real herdr, and repeating the dispatch does not duplicate agents.

## Decision

- **Atomic claim** (`claimRun`, db). Runs in an `IMMEDIATE` transaction. First it compares `expected` with the task: repeating an already applied decision returns `stale_state`. Then it checks that the phase corresponds to the state (`phase_mismatch`) and that no other Run remains open (`run_active`; the unique index already prevented it). Finally it revalidates the limits with `Occupancy` over a snapshot read on the same connection (nested savepoint). If everything adds up, it applies `dispatch` and creates the Run with a token (256 bits, hex), iteration, the profile's model, agent name and session id. If something does not add up, it writes nothing.
- **`dispatch` resolves when the claim is confirmed.** The rest of the sequence (worktree with its bootstrap, which can take minutes) runs in the background. This way the scheduler is not blocked and the next pass already sees the slot occupied. The failures of that part go to `onError` with their Run.
- **Resumable dispatch.** Each step is recorded in the Run: `herdr_pane`/`herdr_workspace` when opening the pane and `launched_at` (new column) when sending the prompt. `launch(runId)` skips what is already done:
  - If herdr already has an agent with the Run's name, it reuses it.
  - If the stored pane is still open and without an agent, the agent starts there.
  - It only sends the prompt to an `idle` agent. One that is `working`, `blocked` or `done` has already received it.

  - A freshly started agent that is still loading (herdr returns `agent_not_ready` with `working` or `unknown`) is awaited until `idle` or `blocked` before deciding.
  - A stored pane is only reused if it is still in the workspace and the worktree's checkout, because herdr reuses ids after restarting.

  If the Run is closed while launching (a cancellation during the bootstrap), the launch stops at the next step and closes what it opened. `recover()` relaunches the open Runs without `launched_at`. `Orchestrator.start()` calls it on startup. A lock per Run prevents `recover` and `dispatch` from launching the same one at once.
- **Agent name.** `t<12 hex of the task id>-<phase>-<n>`, with `n` the Run's ordinal in that phase. herdr limits names to `^[A-Za-z0-9_-]{1,32}$` and a full UUID does not fit. 48 bits of the id make a collision unlikely. If it happens, the metadata detects it: an agent with that name whose `run` token belongs to another Run (or whose pane is not the stored one) is not adopted, and the Run fails with `agent_name_taken`.
- **Environment and args.** The pane is created with `pane split --env` and the variables `LUNASQ_RUN_TOKEN`, `LUNASQ_TASK_ID`, `LUNASQ_RUN_ID` and `LUNASQ_PHASE` (constants in `@lunasq/schemas`), plus the process's extra ones (`paneEnv`). Claude Code's args are built like this: `--model <profile's model>`, the profile's args, `--mcp-config <file> --strict-mcp-config` and `--session-id <uuid>`. A profile that already brings any of those flags fails with `profile_conflict`.
- **Auto mode (pending from ADR 0008).** The dispatcher neither injects nor requires it: it lives in the profile's args, as `docs/design.md` §Decisions made says. The dispatcher only sets what the contract with LunasQ needs: MCP and session.
- **Folder trust (pending from ADR 0004).** If `agent start` leaves the agent `blocked`, the dispatcher reads the screen (`agent read`). Only if it recognizes the trust dialog (`showsTrustDialog`: «Yes, I trust this folder» next to «No, exit») does it send `down enter` with the adapter's new `sendKeys` and wait for `idle`. The cursor starts on «No, exit», so a bare Enter would close Claude Code. Any other `blocked` in a freshly started agent is not touched: the Run fails with `agent_blocked`. In a reused agent (crash after the prompt), a `blocked` is a phase permission and is respected. Pre‑accepting the folder in `~/.claude.json` was discarded, because that file is written by the Claude processes that are running. UW-28 can add it as an optimization.
- **Session identity.** The dispatcher sets the native session id (`--session-id`, source `native`) in the claim. On closing, if the Run has no native id, it uses the `agent_session` that herdr reports (`herdr`) or the agent's name (`name`). The new column `runs.agent_session_source` stores the source.
- **Project workspace.** The new column `projects.herdr_workspace_id` is read and written with `ProjectWorkspaceRepository` (port `ProjectWorkspaceStore` in domain). It is not configuration: `ProjectRepository` does not expose it. `WorktreeService` passes the stored id to `ensureWorkspace` only if it is still a main workspace with the project's label or with a pane in its checkout: herdr reuses ids such as `w1` after restarting. Then it stores the resulting one, so a renamed project does not duplicate its workspace. Without the store, it keeps searching by label.
- **Phase closing.** `closeRun(runId, {result, handoff?, failureReason?})` stores result, handoff and session identity and closes the pane, and with it the agent. It is idempotent: the first close wins. A Run's closes are serialized among themselves, without waiting for the launch. The pane is only closed if it is still the Run's: it has its agent, or is empty in its workspace and in its worktree. It does not transition the task. On an already closed Run it only cleans up the pane. `failRun(runId, reason)` closes the Run as failure and, if the task is still running in that phase, applies `run_failed` with the phase's consecutive failures, counted from the last successful Run or the last `resume`, according to ADR 0007. It uses the same `consecutiveFailures` as `report_failure` (UW-15) plus one for the Run that fails: this way it counts even if it starts in the same millisecond as the `resume`. It also closes the pane. A failure on launch (bootstrap, herdr, profile) uses `failRun`.
- **Observation.** The `RunObserver` port (`watch` on launch, `unwatch` on close) is for UW-17. Signals, nudges and timeouts are outside this unit.
- **MCP file.** `ensureMcpConfig(path, url)` writes ADR 0002's file only if it is missing or changed, with an atomic rename. `Orchestrator.start()` ensures it before dispatching. The path and the URL are set by whoever starts the process (CLI, UW-28).
- **Composition.** `Orchestrator` builds `WorktreeService` (with the workspaces store), `PhaseDispatcher` and `Scheduler` with the same limits. `start()` ensures the MCP file, calls `recover()` and starts the scheduler. `stop()` stops the scheduler and waits for the launches in progress. The outbox publisher is started by whoever creates it.
- **Integration with the LunasQ MCP (ADR uw-15-mcp-tools).** The exit tools close the Run in the same transaction as the transition. The dispatcher does not close it again: the `Orchestrator` subscribes to `task.transitioned` in the outbox. When the task leaves `running` and its last Run is already closed, it calls `releaseRun`, which stops the agent and closes the pane. An open Run (the verifier with a pass, ADR 0007) is not touched. `RunRepository`, `closeRun` and `consecutiveFailures` are UW-15's, extended with what the dispatcher needs (`forTask`, `active`, `latestForTask`, `recordPane`, `markLaunched`, `close`, `fail`, the session identity in `closeRun`).
- **`MCP_TOOL_TIMEOUT`.** `submit_for_verification` runs the test gate inside the call (20 min by default). The dispatcher sets `MCP_TOOL_TIMEOUT` in the pane to that timeout plus 5 minutes (`DEFAULT_MCP_TOOL_TIMEOUT_MS`); `paneEnv` can change it.
- **Migration 0004 edited by hand.** It goes after UW-15's `0003_runs_context_read`. drizzle-kit recreated `runs` copying nonexistent columns, and the `DROP` would have cascade-deleted the `usage_records`. `ADD COLUMN` with CHECK is used, as in 0002.

## Consequences

- **UW-15**: no changes to its tools. They close the Run and the dispatcher cleans up the pane on seeing the transition through the outbox, so the `OutboxPublisher` must be running alongside the `Orchestrator`.
- **UW-10**: the `before_*` points on dispatch and `on_failure` when a Run fails do not yet call `HookService.run`. They remain pending in this unit or another.
- **UW-17**: implements `RunObserver` (per‑pane subscription, phase timeout) and uses `failRun` on a crash. Reconciliation can rely on `RunRepository.active()` and on `launch` to relaunch.
- **UW-28**: chooses the MCP file's path and the server's URL and passes them to the `Orchestrator`. `doctor` can warn if the trust dialog changed its text, because then the dispatcher would fail with `agent_blocked`.
- **Known window:** if the process crashes between `promptAgent` and `launched_at` while the agent is still `idle`, `recover` repeats the prompt. With Claude Code the agent goes to `working` immediately, so the window is minimal.
- **Risk with `--session-id`:** the native id is set in the claim. If the process crashes after Claude Code created the session and a new agent has to be started in that Run, it is passed the same id, and Claude Code might reject it as in use. It is not verified. The pilot (UW-29) covers it; if it fails, a new id is generated when starting a fresh agent.
- **Not tested with real Claude Code in this unit:** that `--session-id` coexists with `herdr agent start` and that the `${VAR}` header is expanded. The expansion was proven in ADR 0002's spike with herdr. UW-16's real suite (`pnpm --filter @lunasq/server test:herdr`) uses a `claude` stub that reproduces the trust dialog and records args and token. The pilot (UW-29) covers it with real Claude Code.
