# UW-24 — Archivo de evidencia: se escribe al cerrar cada Run, queda sin commitear y lo commitea la entrega

- Estado: aceptada
- Fecha: 2026-10-29
- Unidad: UW-24 · Código: `packages/server/src/evidence/`, `packages/schemas/src/evidence.ts`, `evidence` en `PhaseDispatcher` y `Orchestrator`, `commitPaths` y la exclusión de `lunasq/tasks/` en `packages/adapters/src/git/`, `uncommitted` en `packages/server/src/mcp/ports.ts`

## Contexto

`docs/design.md` (§Archivo de evidencia) pide `lunasq/tasks/{id}.md` en el worktree de la tarea, con una sección por Run que se agrega al cerrarlo, para que viaje en el branch y en el PR y sobreviva al cierre del pane de herdr y a la retención de transcripts de Claude Code. ADR uw-10-hooks, uw-11-gate-tests y uw-19-revisores dejaron el material en el Event log y en `run_subagents`.

El archivo está dentro del repo, y tres piezas ya hechas miran el estado de git del worktree:

- `submit_for_verification` y `submit_verdict` con pass rechazan con `dirty_worktree` si hay cambios sin commitear (UW-15, UW-23).
- El pass compara el `HEAD` con el commit que pasó el gate de `submit_for_verification`: un commit de evidencia entre medias da `head_changed` (UW-23).
- `HookService` no commitea lo que dejan los hooks si el worktree ya estaba sucio (UW-10).

## Decisión

- **Una sección por Run, reescrita en su lugar.** `EvidenceService.recordRun(runId)` arma la sección del Run cerrado y la inserta o reemplaza entre los marcadores `<!-- lunasq:run:start <id> -->` y `<!-- lunasq:run:end <id> -->`. Repetirlo con los mismos datos no cambia el archivo, así que reintentos y reconciliación son seguros. Las secciones quedan en orden de primer cierre; el encabezado (tarea e intent) se regenera y lo que no sea una sección se descarta. Un Run abierto, inexistente o de una tarea sin worktree se salta sin error. Las escrituras de una misma tarea van en orden (`KeyedLock`) y el archivo se escribe a un temporal y se renombra.
- **Contenido de la sección** (`renderRunSection`, función pura): fase, agente, modelo, iteración, inicio, fin, resultado, `failure_reason` y sesión; el handoff como bloque JSON; en verificación, el veredicto completo (por criterio, reporte o justificación de cada revisor, must-fix y hallazgos refutados con su motivo; si el handoff no valida contra el esquema vigente cae al JSON); la salida de cada ejecución del gate (`test_gate.executed`) y de cada hook (`hook.executed`, `hook.point_completed`) del Run, leídas del Event log; y los transcripts. Solo entran los eventos cuyo `runId` es el del Run.
- **Transcripts.** `ClaudeTranscriptSource` lee `~/.claude/projects/<cwd con no alfanuméricos → "-">/<session>.jsonl` (también por la ruta real del worktree) y, por cada subagente, el `transcript_path` que guardó el hook `SubagentStop` (ADR uw-19-revisores). `transcriptToMarkdown` conserva turnos de usuario y agente, llamadas a tools y sus resultados; omite el razonamiento interno y los mensajes de metadatos, recorta los resultados de tools (principio y final), los bloques de texto y el transcript entero, y va dentro de un `<details>` por transcript. Un transcript que falta o que pesa más de 32 MiB deja una nota en su lugar. **El `transcript_path` lo manda un hook que cualquiera con el run token puede llamar, así que solo se lee si es un `.jsonl` cuya ruta real queda en el directorio de proyecto de este worktree dentro de `~/.claude/projects/`** (sin seguir symlinks fuera): si no, se podría volcar al PR un archivo arbitrario o el transcript de otra tarea.
- **Redacción de secretos** (`redactSecrets`) sobre toda la sección, no solo los transcripts: la salida del gate, los hooks y el handoff también pueden traer secretos. Patrones al estilo gitleaks: llaves privadas (también cortadas), tokens de GitHub, AWS, Anthropic, OpenAI, Slack, Stripe, Google y npm, JWT, `Bearer`, credenciales en URLs, el run token (header y variable de entorno) y asignaciones a nombres como `secret`, `token`, `password`, `api_key` (se conserva el nombre y se redacta el valor). Además se redacta el run token del propio Run de forma literal. Es idempotente. Los transcripts se redactan **antes** de recortarlos (un recorte puede dejar fuera el BEGIN de una llave y el resto ya no casaría con ningún patrón), y además hay una regla para el cuerpo huérfano de una llave (líneas base64 + END). Los valores entre comillas se redactan completos, también con comillas escapadas (JSON dentro de JSON), y se cubren `Basic` y `-p<contraseña>`. Las reglas tienen cuantificadores acotados para no degradar en textos largos. Prefiere redactar de más: el archivo queda en el historial de git. No es infalible; un secreto sin forma reconocible pasa.
- **Marcadores a prueba de contenido del agente.** Cualquier `<!-- lunasq:` que venga en un transcript, un handoff o el intent se reescribe como `<!-- lunasq-escapado:`, para que un agente no pueda cerrar su sección antes de tiempo ni plantar la de otro Run.
- **Quién lo llama.** `PhaseDispatcher` recibe `evidence?: RunEvidenceSink` y llama `recordRun` en `closeRun`, `failRun` y `releaseRun`, después de cerrar el Run **y de cerrar el pane**, así el agente ya está detenido y su transcript completo (una tool de salida del MCP cierra el Run mientras el agente termina su turno); si cerrar el pane falla, la evidencia se escribe igual. Esos tres cubren los cierres: los del dispatcher y la reconciliación (`closeRun`, `failRun`, incluidos los fallos al lanzar) y los de las tools de salida del MCP, que cierran el Run en su transacción y a los que el `Orchestrator` llega con `releaseRun` al salir la tarea de `running` (ADR uw-16-dispatcher). `Orchestrator` pasa `evidence` al dispatcher. Un fallo al escribir se reporta por `onError` y no impide cerrar el Run ni el pane. El veredicto con pass deja su Run abierto hasta la entrega (ADR 0007): su sección se escribe cuando UW-26 lo cierre.
- **El archivo queda sin commitear durante el loop.** `GitAdapter.isDirty` y `commitAll`, y `GitCommitVerifier.uncommitted`, ignoran `lunasq/tasks/` con un pathspec `:(exclude)`. Así el archivo no dispara `dirty_worktree` ni hace que `HookService` se salte el commit de sus cambios. El pass tolera que el `HEAD` haya avanzado desde el gate de `submit_for_verification` cuando todos los commits intermedios tocan solo `lunasq/tasks/` (`GitCommitVerifier.onlyEvidenceBetween`); el gate del pass corre igual sobre el `HEAD` actual, así que el veredicto sigue juzgando el código que se prueba. Antes del rebase, la entrega commitea la evidencia pendiente para que lo trackeado no ensucie el worktree, y vuelve a commitearla tras cerrar el Run del verificador. Se descartó commitearlo en cada cierre (agregaba ruido y exigía relajar más el gate) y escribirlo fuera del worktree (contradice el diseño y obliga a copiarlo en la entrega).
- **Escritura segura.** El worktree es del agente: antes de escribir se comprueba con `lstat` que `lunasq/` y `lunasq/tasks/` no sean symlinks (si lo son, `recordRun` rechaza y el dispatcher lo reporta), y el temporal tiene nombre aleatorio y se abre con `wx`; si falla, se borra.
- **Commit.** `GitAdapter.commitPaths({ cwd, paths, message, trailers })` agrega con `--force` (el proyecto puede ignorar `lunasq/tasks/` en su `.gitignore`) y commitea solo esas rutas con `--only`, sin tocar lo demás del índice ni del working tree; devuelve null si no hay cambios. `EvidenceService.commit(taskId)` la usa para el archivo de la tarea con los trailers `LunasQ-Task` y `LunasQ-Run` (último Run). FakeGit y RealGit cumplen la misma suite de contrato.
- **Constantes compartidas** en `packages/schemas/src/evidence.ts`: `EVIDENCE_DIR`, `evidencePath` y los trailers `COMMIT_TRAILER_TASK` y `COMMIT_TRAILER_RUN`, que `HookService` ya usaba como constantes locales.

## Consecuencias

- **Limitación: Run cerrado por el MCP con otro Run ya abierto.** `Orchestrator` llama `releaseRun` solo para el último Run de la tarea al recibir `task.transitioned`. Si el mensaje del outbox se entrega tarde (reinicio, retraso) cuando la tarea ya tiene un Run nuevo, el Run anterior cerrado por el MCP no pasa por `recordRun`. `recordRun` es idempotente, así que UW-29 puede cerrar el hueco con un barrido de la reconciliación.
- **Limitación: las secciones previas se conservan del disco tal cual.** El worktree es del agente, que podría editar o borrar la sección de un Run anterior antes de la entrega. Se acepta en v1: el archivo lo revisa el humano en el PR y el Event log y la tabla `runs` son la fuente de verdad. Regenerar todas las secciones desde la base en cada cierre es la mejora si hace falta.

- **UW-26** debe llamar `EvidenceService.commit(taskId)` antes del push de la entrega, después de cerrar el Run del verificador (para que su sección esté) y después del gate final, y volver a llamarlo si la entrega cierra más Runs. El commit entra al branch y al PR.
- **UW-29** compone `EvidenceService` (con `RealGit` y `ClaudeTranscriptSource`) y lo pasa como `evidence` a `Orchestrator`.
- Un agente que ejecute `git add -A` en su worktree puede commitear el archivo a medias dentro de su propio commit; la historia del branch puede mostrarlo en un commit del agente. `commitPaths` commitea la versión final y, si ese commit ocurre después del gate de `submit_for_verification`, el pass lo acepta solo si no toca código. Un archivo ya trackeado que cambia después del commit queda como cambio sin commitear y bloquea cualquier `git rebase` del agente o de la entrega: por eso la entrega commitea la evidencia pendiente antes del rebase.
- Si el worktree se borra antes del cierre de un Run (cancelación con limpieza), no hay dónde escribir y la sección se pierde; el Event log y la tabla `runs` conservan los datos.
- El formato de línea de los transcripts de Claude Code no es un contrato estable. El convertidor lee solo `type`, `message.content` y `timestamp`, y salta lo que no reconoce; una línea ilegible se cuenta en una nota.
