# ADR — Settings: agent providers, concurrency limit and verification iteration cap

- Status: accepted
- Date: 2026-11-01
- Code: `packages/schemas/src/settings.ts` (`AgentProviderSettings`, `settings.updated`), `packages/db/src/settings.ts` and migration `0011_settings_proveedores`, `packages/domain/src/providers.ts` (`effectiveAgentKind`, `enabledFallbackOrder`), `packages/domain/src/scheduler.ts` (`schedule`, `Occupancy`), `packages/db/src/runs.ts` (`claimRun`), `packages/server/src/dispatcher/dispatcher.ts` (`startAgentWithFallback`), `packages/server/src/api/settings.ts`, `packages/web/src/pages/settings.tsx`; concurrency: `ConcurrencySettings` (`packages/schemas/src/settings.ts`), `readConcurrencySettings` and `SettingsRepository.saveConcurrency` (`packages/db/src/settings.ts`)

## Context

When Claude Code's or Copilot CLI's usage limit is exhausted, the scheduler kept dispatching tasks to that provider: each one started, hit the limit and consumed a Run and retry cycle needlessly. The human needs to turn a provider off by hand, without touching each project's configuration.

## Decision

- **Global configuration.** `AgentProviderSettings` is an `enabled` boolean for each `AgentKind` (default all `true`). It is stored in the `app_settings` table (key `providers`, JSON value validated with Zod on read and write). Without a stored row, all are enabled. Saving is an upsert: repeating the same configuration leaves the same state.
- **Effective provider.** The primary is the phase profile's `kind`. The fallback order is the primary and then the other `AgentKind`s in registration order, filtered by enabled; the effective one is the first in that list, or none. `domain` exposes `effectiveAgentKind` and `enabledFallbackOrder` and does not know the database: `schedule`, `Occupancy` and the claim receive the enabled providers as data.
- **Scheduler.** Reads the configuration on every pass. The slot and the `agentKind` of each decision use the effective provider, so the per‑agent‑type limit applies to the provider that will really run. With all disabled the plan has no dispatch decisions: the tasks stay in `queued` (they are not paused with a new state, they are simply not dispatched). Live agents count against the provider they really run with (`SchedulerTask.agentKind`, the `agentKind` of their open Run, which may be a fallback); if missing, against the primary of their profile.
- **Claim.** `claimRun` rereads the configuration inside its transaction (the human may have changed it after planning). Without an effective provider it rejects with `providers_disabled`, without touching the task or creating a Run. The Run is created with the effective provider, and the profile's model is only applied if it is the primary.
- **Launch.** `startAgentWithFallback` reads the enabled providers right before starting each one, and again after preparing the pane (that preparation waits for herdr and disk): a disabled provider is not attempted and leaves no attempt record, and the already prepared pane is closed. If the human turned all off during the launch, it is not a CLI failure: `RunRepository.pause` closes the Run as `cancelled` (it does not count for retries) with the reason `all providers are disabled in Settings` and the task goes back to `queued`, just like when the scheduler pauses dispatch. If enabled providers remain but none starts, the Run fails and the task moves to `needs_human` via `providers_unavailable`.
- **Live agents untouched.** Changing the configuration never interrupts or closes a Run in progress; it only affects new dispatches and launches.
- **API and event.** `GET` and `PUT /api/settings/providers`. The PUT accepts a partial change (only the kinds it carries) that is applied over what is current inside the transaction: each UI switch sends only its provider, so two tabs with stale views do not overwrite each other (400 `invalid_input` if the body carries an unknown kind or a non‑boolean value; what is stored does not change). Saving records `settings.updated` in the Event log and the outbox in the same transaction; the scheduler, subscribed to all topics, runs a pass and dispatches with the enabled provider.
- **`events.task_id` becomes nullable** (and `OutboxMessage.taskId` too): `settings.updated` is a global event without a task. The outbox consumers that operate on a task ignore messages with a null `taskId`, and `changesSince` does not count them as a task change. The migration rebuilds `events`, recreates the append-only triggers and backs up and restores `outbox` (with `INSERT OR IGNORE`): Drizzle migrates inside a transaction, where `PRAGMA foreign_keys=OFF` has no effect, and with foreign keys active the `DROP TABLE events` would cascade-delete the outbox rows; `migrateDatabase` turns them off, and then the restore duplicates nothing.
- **UI.** Page `/settings` with a switch per provider (linked in the navigation) (the off state with enough contrast; after saving it rereads the configuration instead of overwriting the cache with the PUT's response) and a global «Despacho en pausa» notice with a link to Settings when both are disabled.

## Consequences

- Disabling only one provider applies the fallback rules of [ADR 0016](0016-proveedores-agente.md); disabling both is equivalent to pausing dispatch without losing the queue.
- A task whose profile uses a disabled provider runs with the other: the primary's profile flags (`args`) are not transferred, as in any fallback. Verification with reviewers remains Claude‑only (ADR 0016), so a verification dispatched to Copilot because of a disabled one inherits that limitation.
- Adding a new `AgentKind` makes it appear in the configuration with default enabled and in the Settings page without schema changes.
- There is no automatic enabling when the usage limit renews: the human reactivates the provider from Settings.

## Origin of the requests

`/api/settings/*` has no authentication and mutates state that pauses dispatch, so it rejects with 403 `forbidden_origin` any `Host` or `Origin` that is not `localhost`, `127.0.0.1` or `[::1]` (defense against DNS rebinding, like the MCP). Since `Host` and `Origin` are set by the client, it also requires the connection to come from loopback (the socket's address): with the server bound to another interface, a remote client cannot bypass the guard by forging `Host: localhost`.

If reading the configuration fails, the global notice says so («Estado del despacho desconocido») instead of disappearing, also when there is cached data indicating an enabled provider (the last thing seen may have changed). The Settings page keeps the switches with the last state read and warns about the read error.

## Fallback and concurrency

The claim reserves the slot of the provider effective at that moment. If the launch moves to another provider (a fallback after a startup failure, or because Settings changed), `RunRepository.switchAgentKind` revalidates in an immediate transaction the global, project, phase and agent‑type limits against the other live agents; a provider whose slot is full is skipped. If for that reason none started and no provider failed to start, it is transient saturation, not a CLI failure: the Run is closed as `cancelled` (without counting retries) and the task goes back to `queued` until a slot is freed, instead of escalating to `needs_human`. If some provider did fail to start (even if another was left without a slot), the Run fails and counts like any other case without an available provider: pausing it would hide the failure and the scheduler would retry the broken provider without backoff.

## Global concurrency limit

The human also sets from Settings how many agents can live at once, without restarting the server.

- **Configuration.** `ConcurrencySettings` is `{ globalConcurrency }`, an integer from 1 to 50 (strict: a decimal, a text or an unknown field is invalid). It is stored in `app_settings` (key `concurrency`), without a new migration. Without a row (or with a stored value that no longer validates), the **effective limit** is `SchedulerConfig`'s `globalConcurrency` (default 5); the one that starts the server serves as the fallback and Settings overrides it.
- **Scheduler.** Reads the effective limit on every pass and passes it to `schedule`. Live agents (including `waiting_human` ones) count against it.
- **Claim and fallback.** `claimRun` and `RunRepository.switchAgentKind` read the effective limit inside their immediate transaction: the plan may have been made with an earlier limit. If it no longer fits, the claim rejects with `no_slot` without creating a Run and the task stays in `queued`; a provider change by fallback is rejected for lack of a slot with the stored limit, not with the default.
- **Raising and lowering.** Raising the limit immediately dispatches the queued tasks until the new slots are filled: the `settings.updated` wakes the scheduler. Lowering it never interrupts, pauses or closes a Run; it only prevents new dispatches while the live ones reach or exceed the limit.
- **API and event.** `GET /api/settings/concurrency` returns `{ globalConcurrency }` and `PUT` stores it (400 `invalid_input` if it is not an integer from 1 to 50 or carries unknown fields; what is stored does not change), with the same local‑origin guard as the rest of `/api/settings`. Saving a value different from the current one records `settings.updated` with `globalConcurrency` in the payload, in the Event log and the outbox in the same transaction; saving the current one writes and publishes nothing. The `settings.updated` payload admits `providers`, `globalConcurrency` or both (at least one), so old events with only `providers` remain valid.
- **UI.** The «Concurrencia» section of `/settings` shows the current limit in a numeric field with a Save button. An empty value, 0, a decimal or greater than 50 sends nothing and shows a message tied to the field; the button is disabled while saving and, as with the providers, the field rereads the configuration instead of overwriting the cache with the PUT's response. Read and save errors are shown in a `role=alert` notice without losing the last value read, and the providers section keeps working.

## Global verification iteration cap

The human also sets from Settings how many reworks the verification loop allows before a reject escalates the task, without restarting the server.

- **Configuration.** `VerificationSettings` is `{ maxVerificationIterations }`, an integer from 1 to 20 (strict: a decimal, a text or an unknown field is invalid). It is stored in `app_settings` (key `verification`), without a new migration. Without a row (or with a stored value that no longer validates), the global cap is `DEFAULT_MAX_ITERATIONS` (5, previously 3).
- **Effective cap.** `maxVerificationIterations(project, globalCap)` in the domain returns the project's `limits.maxVerificationIterations` if defined, otherwise the global cap, otherwise 5. A defined project cap always overrides the global one.
- **Where it applies.** `submit_verdict` (reject → `verdict_rework`) and the delivery conflict cap (`delivery_failed` after as many consecutive conflicts as the cap) read the global cap with `readVerificationSettings` at decision time. Changing it never interrupts Runs in progress; it applies to the next verdict or delivery decision. `resume` with `resetIteration` still grants a full cycle of the effective cap.
- **API and event.** `GET /api/settings/verification` returns `{ maxVerificationIterations }` and `PUT` stores it (400 `invalid_input` if it is not an integer from 1 to 20 or carries unknown fields; what is stored does not change), with the same local‑origin guard as the rest of `/api/settings`. Saving a value different from the current one records `settings.updated` with `maxVerificationIterations` in the payload, in the Event log and the outbox in the same transaction; saving the current one writes and publishes nothing. `SettingsUpdatedPayload` accepts `providers`, `globalConcurrency`, `maxVerificationIterations` or any combination (at least one), so old events remain valid.
- **UI.** The «Iteraciones de verificación» section of `/settings` follows the concurrency section: a numeric field with its own save button, a field message for an empty value, 0, a decimal or greater than 20 (nothing is sent), and `role=alert` notices for read and save errors. The project form's iterations field says that leaving it empty uses the global value. Texts in both dictionaries (ES/EN).
