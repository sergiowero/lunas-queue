# 0007 — State machine and Event log

- Status: accepted
- Date: 2026-10-29
- Unit: UW-04 · Code: `packages/domain/src/state-machine.ts`, `packages/db/src/task-transitions.ts`, `packages/db/src/event-log.ts`, `packages/schemas/src/events.ts`, `packages/db/drizzle/0001_events_append_only.sql`

## Context

`docs/design.md` (§State machine) defines the states, the sub‑states and the transition table, but leaves open the exit from Needs human, the return to In progress because of delivery conflicts, the counting of iterations and retries, and how to guarantee that no transition happens without its event.

## Decision

- **Commands.** The state machine receives 16 commands (`TaskCommand` in `@lunasq/schemas`). Twelve change the state: `submit_spec`, `request_changes`, `approve`, `submit_for_verification`, `submit_result`, `verdict_rework`, `verdict_pass`, `delivery_conflict`, `escalate`, `cancel`, `pause` and `resume`. Four change only the sub‑state: `dispatch` (queued → running), `ask_human` (running → waiting\_human), `answer` (waiting\_human → running if the agent is still alive, or queued if not) and `run_failed` (running → queued).
- **Pure domain.** `transition(snapshot, command, actor)` has no effects: it returns the next state and the event, or an error `invalid_transition`, `actor_not_allowed` or `guard_failed`, in that order of precedence. The guards receive facts already computed by the caller (complete spec, approved version, test gate, test coherence, criteria, commits, PR); UW-11, UW-12, UW-23 and UW-26 compute them.
- **Actors.** Each command has its allowed actors (`COMMAND_ACTORS`), according to the design's table. `verdict_pass` is emitted only by the system: the verifier records its verdict in the handoff (UW-23) and delivery (UW-26) emits the pass after creating the PR, with the fact `verifierPassed`; the agent cannot know whether the PR was created.
- **Origins.** The commands that close a phase (`submit_spec`, `submit_for_verification`, `verdict_rework`, `verdict_pass`, `delivery_conflict`) require `running`: the phase's Run is still open. This way nobody can complete a task in `verification/queued`, the one that does not have a verifier yet. Delivery runs while the verifier's Run is open, and that Run is closed after the transition; reconciliation (UW-17) must not treat that interval as a fallen Run.
- **Sub‑state.** Only draft, in\_progress and verification carry a sub‑state, and they are entered in `queued`; the rest have it as `null`. An incoherent snapshot rejects every command.
- **Iterations.** `verificationIteration` is the cumulative count of reworks: it never decreases, not even when the human resumes the task, so the UI, the Runs and the events show the real amount of iterations. `verificationCycleStart` is the iteration at which the current verification cycle began (0 until the task is resumed after exhausting its iterations); it is never greater than the iteration. `verdict_rework` with `verificationIteration - verificationCycleStart` lower than the maximum goes back to in\_progress with iteration + 1; otherwise it goes to needs\_human with `reason: iterations_exhausted` and the iteration unchanged. The caller passes the effective maximum (the project's `limits.maxVerificationIterations`, else the global cap saved in Settings, else `DEFAULT_MAX_ITERATIONS`, now 5; see [ADR settings-proveedores](settings-proveedores.md)). With the default, five reworks fit per cycle: a task that exhausts a cycle at iteration 5 and is resumed reworks to 6, 7, 8, 9 and 10, and escalates at the next one.
- **Retries.** `run_failed` carries `attempt`, the consecutive failed Runs of the phase counting this one; the caller counts them from the last successful `dispatch` or `resume`. Up to `maxRetries` (default 3) the task goes back to queued; the next failure sends it to needs\_human with `reason: retries_exhausted`.
- **Needs human.** `escalate` applies from any non‑terminal state except needs\_human and paused, with an `EscalationReason`. The human leaves with `resume`, which returns to the state before the last escalation (read from that event's `from`) with its initial sub‑state, or with `cancel`. `resume` keeps the iteration and the cycle start, unless it carries `newCycle`, which sets the cycle start to the current iteration (the iteration itself is not touched) and grants a full verification cycle. Resuming after `iterations_exhausted` goes to `in_progress` and applies `newCycle` automatically: the agent must fix the must‑fix and has another full cycle of reworks (the effective cap); otherwise, the first reject would escalate again immediately. The resume event carries the unchanged cumulative `verificationIteration`.
- **Pause.** `pause` is emitted only by the human and applies from draft, refined, in\_progress and verification with any sub‑state; completed, cancelled, needs\_human and paused reject it with `invalid_transition`. It leaves the task in `paused` with sub‑state `null` and the same iteration. From verification it carries the fact `deliveryInProgress` (the verifier's Run is still open with its pass stored, which `RunRepository.deliveryInProgress` computes): with it, it is rejected with `guard_failed`, because pausing would leave the PR half‑done. There is no confirmation in the UI. `POST /api/tasks/:id/pause` always emits with a human actor: that only the human pauses (AC-3) is enforced by the domain (`transition` rejects a system or agent `pause` with `actor_not_allowed`), not by the API. The REST API does not authenticate the caller: it listens on `127.0.0.1` and is the human's channel, like `cancel` and `resume`; a local process that calls it can pause. It is a known risk and authenticating the API is outside this spec. `paused` is a new state in `TaskState` and in the CHECK of `tasks.state` (migration `0010_task_paused`).
- **Leaving Paused.** Only `resume` or `cancel`; `escalate` (for example the scheduler's, because of a closed dependency) and the other commands are rejected, and the scheduler and dependency escalation skip paused tasks. `resume` returns to the previous state read from the `from` of the last event that entered paused (or needs\_human, depending on where the task is), with its initial sub‑state and the iteration kept; the phase is redispatched from scratch on the same worktree. Like any `resume`, resuming resets the consecutive failure count that feeds `run_failed`'s `attempt`.
- **Effects of the pause.** The domain does not perform them: the reconciler (which wakes on `pause` from the outbox) closes the open Run as `cancelled` with `task_left_phase` and releases the pane, without touching the worktree or the branch (only cancelled and merged ones are removed). The open Question of a task in `waiting_human` is canceled as on any exit from that sub‑state. The Inbox does not include paused ones.
- **Tasks without code: `submit_result`.** A task whose deliverable is not a change in the repo (an investigation or synthesis, an already implemented request, or an unresolvable one) ends with `submit_result`, an MCP tool accepted in the refine and implement phases (in verify it answers `tool_not_allowed`). The state machine admits it only for the agent and from `draft/running` or `in_progress/running`; it leads to `completed` without going through Refined, verification, delivery or a PR (another origin or actor gives `invalid_transition` or `actor_not_allowed`). The result kind travels in the `task.transitioned` event's `note`.
  - **Result.** The task stores `result_kind` (`research`, `already_implemented` or `not_resolvable`) and `result` (Markdown of up to 20,000 characters), both `null` if it was delivered with a PR. A task never has both a Result and a PR. They are written together with the transition, the closing of the Run with its handoff and, if missing, the title (`task.titled`), in a single transaction (`completeTaskWithResult`). Migration `0012_task_result` recreates `tasks` because of the `result_kind` CHECK, like `0010`.
  - **Handoff.** `submit_result` receives its own handoff, validated with Zod (`ResultHandoff`, `result.json`): `schemaVersion`, `taskId`, `runId`, `phase` (`refinement` or `implementation`, the Run's), `summary`, `title`, `resultKind` and `result`. An invalid handoff gives `invalid_handoff` with the field's path and one with a foreign taskId, runId or phase gives `handoff_mismatch`; the Run stays open.
  - **Code guard.** From implementation it is rejected with `branch_has_commits` if the task's branch has commits that are not in the base branch (local or `origin/<base>`); if it cannot be checked, it is also rejected. With code, the exit is `submit_for_verification`. The uncommitted worktree is not checked.
  - **Dependencies.** The scheduler satisfies a dependency with its merged PR or with the task `completed` with a Result. Releasing the worktree and the reconciler's pass apply just as with a merge.
- **Delivery conflicts.** `delivery_conflict` returns from verification to in\_progress without raising the iteration: it is not a verifier rework.
- **Terminals.** completed and cancelled accept no command; `cancel` does not apply to completed. `cancel` does apply to paused.
- **Event.** Every transition is recorded as `task.transitioned`, with payload `{command, from, to, verificationIteration, reason?, note?}`. The domain validates the event with `TaskTransitionedEvent` before returning it and answers `guard_failed` if it does not comply (empty note or one over 2000 characters, reason outside the enum): only what can later be read enters the log. Other event types (for example `task.created`) are written with `appendEvent` and do not change state.
- **Persistence.** `transitionTask` is the only way to change state, sub‑state, iteration or cycle start (`tasks.verification_cycle_start`, migration 0016, with CHECKs that make it unsigned and not greater than the iteration). It runs in an `IMMEDIATE` transaction, which takes the write lock before reading the task: it applies the domain, does the update conditioned on the state read and appends the event. If the event fails, the task is rolled back. The optional `expected` parameter rejects with `stale_state` if the task is no longer where the caller saw it. Repeating an already applied command gives `invalid_transition` and does not duplicate the event.
- **Append‑only in the database.** The custom migration `0001_events_append_only` adds `BEFORE UPDATE` and `BEFORE DELETE` triggers on `events` that abort. Drizzle does not generate triggers; the migration was created with `drizzle-kit generate --custom` and the sync test still passes because the snapshot does not change.

## Consequences

- UW-07, UW-12, UW-15, UW-16, UW-17 and UW-26 move tasks only with `transitionTask` and pass it the facts of each guard.
- UW-08 publishes the outbox from the `task.transitioned` events; the payload schema is already in `@lunasq/schemas`.
- Migration `0010_task_paused` recreates `tasks` (SQLite does not alter a CHECK) and recreates its number triggers. Since drizzle runs each migration in a transaction, where `PRAGMA foreign_keys=OFF` has no effect, the DROP would cascade-delete Runs, edges and usage: `migrateDatabase` turns foreign keys off while migrating, verifies `foreign_key_check` and restores them. `writable_schema` does not work: better-sqlite3 opens in defensive mode.
- Migration `0012_task_result` adds `result_kind` and `result` by recreating `tasks` with the same procedure.
- The database does not prevent a raw `UPDATE` of `tasks.state`; the rule is upheld by convention and review.
